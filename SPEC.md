# Спека: самодиагностика песочницы в ИИ-агенте для кода

10 октября 2026 · Георгий

## Коротко

Когда песочница ИИ-агента не может запуститься, программа должна сама понять причину, попробовать её устранить и объяснить человеку, что делать. Сейчас в таких случаях пользователь видит «неизвестную ошибку» на каждую команду.

Повод: за три дня, с 7 по 9 октября 2026, 177 из 784 обращений к Codex (23%) описывают один и тот же сбой песочницы на Windows. Агент при этом полностью неработоспособен, а перезапуск и переустановка не помогают.

Спека описывает поведение для любого ИИ-агента, который выполняет команды в песочнице. Codex здесь источник данных, а не адресат.

## Проблема

Пользователь просит агента выполнить любую команду, даже безобидную вроде «покажи текущую папку», и получает отказ ещё до её запуска. Так происходит с каждой следующей командой.

Что он видит: строку `helper_unknown_error: setup refresh had errors`. Из неё нельзя понять ни что сломалось, ни чья это вина, ни что делать.

Что он делает дальше, судя по обращениям:

- перезапускает программу или компьютер: об этом пишут в 119 обращениях из 177, и это не помогает;
- переустанавливает программу: 25 обращений;
- просит обходной путь: 39 обращений;
- отключает песочницу и даёт агенту полный доступ к компьютеру. Это самый простой способ продолжить работу, и он снимает защиту, ради которой песочница существует. В [#52000](https://github.com/openai/codex/issues/52000) автор прямо пишет, что режим полного доступа неприемлем как постоянное решение.

Итог для продукта: человек не может работать, не понимает почему, и либо уходит, либо работает без защиты.

## Данные

Сбой описан в 177 обращениях из 784, которые пользователи Codex оставили на GitHub за три дня. Это 23% всего потока жалоб.

| День | Всего обращений | Из них про сбой песочницы | Доля |
| --- | --- | --- | --- |
| 7 октября | 46 | 10 | 22% |
| 8 октября | 387 | 90 | 23% |
| 9 октября | 351 | 77 | 22% |

7 октября попало в выгрузку не целиком, поэтому первая строка неполная.

Что ещё видно в этих 177 обращениях:

- 166 на момент выгрузки открыты, то есть решения пользователи не получили;
- 155 содержат одну и ту же строку ошибки `setup refresh had errors`, 108 содержат код Windows `os error 32`;
- 124 называют один и тот же файл, `node_repl.exe`;
- чаще всего указаны две версии приложения: 26.1002.52244 (89 обращений) и 26.1002.7124 (70).

Люди пишут об одном и том же сбое десятками в день. Вероятная причина: программа не сообщает им, что проблема уже известна.

Самые обсуждаемые обращения: [#51932](https://github.com/openai/codex/issues/51932) (26 комментариев), [#51969](https://github.com/openai/codex/issues/51969) (12), [#51965](https://github.com/openai/codex/issues/51965) (11), [#51862](https://github.com/openai/codex/issues/51862) (11).

## Причина

По описаниям пользователей, программа мешает сама себе. Перед каждой командой песочница проверяет права доступа к служебным файлам приложения. Один из них, `node_repl.exe`, в этот момент уже запущен самим приложением, и Windows отказывает в доступе с кодом 32 «файл занят другим процессом». Проверка не проходит, и команда не запускается.

На это указывают три наблюдения из обращений:

- в журнале песочницы единственная ошибка относится к этому файлу ([#51862](https://github.com/openai/codex/issues/51862));
- файл запущен процессами самого приложения, и они стартуют вместе с ним ([#51969](https://github.com/openai/codex/issues/51969));
- те же команды выполняются, если разрешить их запуск вне песочницы ([#51969](https://github.com/openai/codex/issues/51969)).

Это версия пользователей, разработчик её в собранных данных не подтверждал. Для спеки важна не сама причина, а то, что программа её знала: точный файл и код ошибки были в её журнале, а пользователю показали «неизвестную ошибку».

## Решение

Программа проверяет песочницу заранее, а при сбое проходит пять шагов вместо одной строки об ошибке.

1. **Проверка заранее.** При запуске и перед первой командой программа проверяет, что песочница готова. Пользователь узнаёт о проблеме до того, как поставил задачу.
2. **Распознавание причины.** Сбой относится к одному из типов: файл занят своим же процессом, файл занят чужой программой, не хватает прав, прочее.
3. **Попытка починить самой.** Если мешает собственный процесс программы, она повторяет проверку, а затем перезапускает этот процесс. От пользователя ничего не требуется.
4. **Понятное сообщение.** Если починить не удалось, пользователь видит одно сообщение: что случилось, что программа уже попробовала, что можно сделать сейчас и известна ли проблема разработчику.
5. **Один отчёт вместо сотни.** Кнопка «Отправить отчёт» передаёт разработчику обезличенную диагностику. Одинаковые отчёты склеиваются по подписи ошибки.

Песочница при этом никогда не отключается сама. Запуск без неё возможен только по явному решению пользователя и на ограниченное время.

Пример сообщения для разобранного случая:

> **Команды сейчас не выполняются.** Защищённая среда не смогла запуститься: её служебный файл занят другим процессом приложения. Мы перезапустили его, но это не помогло. Это известная ошибка версии 26.1002, исправление готовится. Ваши файлы и чаты в порядке, переустановка не поможет. [Проверить снова] [Отправить отчёт] [Подробнее]

## Требования

| № | Требование | Зачем |
| --- | --- | --- |
| Т1 | Программа проверяет готовность песочницы при запуске и после каждого обновления, до первой команды пользователя. | Сбой в данных начался после обновления и обнаруживался только на первой команде. |
| Т2 | Каждый сбой настройки получает код причины: файл занят своим процессом, файл занят чужой программой, не хватает прав, прочее. В код входит путь к файлу и ошибка системы. | Без типа причины нельзя ни починить, ни объяснить. |
| Т3 | Если файл занят своим процессом, программа повторяет проверку до 3 раз с паузой, затем перезапускает этот процесс и проверяет снова. | Самый частый случай в данных устраним без участия человека. |
| Т4 | Пользователь никогда не видит «неизвестную ошибку», если причина определена. Сообщение содержит четыре части: что случилось, что уже сделано, что можно сделать, известна ли проблема. Технические детали скрыты за кнопкой «Подробнее». | В 155 обращениях из 177 пользователи пересказывают одну и ту же непонятную строку. |
| Т5 | После сбоя программа показывает постоянный статус «команды недоступны» и не пытается выполнять команды, пока проверка не пройдёт. Агент знает об этом статусе и сообщает о нём, а не повторяет попытки. | Сейчас ошибка повторяется на каждую команду, и агент повторяет попытки впустую. |
| Т6 | Программа не отключает песочницу сама и не предлагает полный доступ как способ исправить ошибку. Запуск одной команды вне песочницы возможен по явному подтверждению, с показом самой команды. | Сбой не должен подталкивать к работе без защиты. |
| Т7 | Кнопка «Отправить отчёт» собирает версию, систему, код причины и фрагмент журнала. Имя пользователя в путях заменяется. Пользователь видит текст отчёта до отправки. | Люди сейчас собирают эту диагностику вручную и сами вычищают из неё личные данные. |
| Т8 | Отчёты с одинаковой подписью (код причины, файл, версия) объединяются в одну запись со счётчиком. Если запись уже есть, пользователю показывается её статус. | Вместо 177 обращений разработчик получает одно с числом пострадавших. |
| Т9 | Программа записывает события: проверка не пройдена (с кодом причины), попытка починки и её исход, выбор пользователя после сообщения. | Без этих событий метрики из раздела ниже не посчитать. |

## Критерии приёмки

Фича принята, если каждый сценарий воспроизводится на тестовой машине с Windows.

1. **Свой процесс, починка удалась.** Служебный файл занят процессом программы. Пользователь отправляет команду. Команда выполняется не позже чем через 10 секунд, сообщения об ошибке нет, в журнале есть событие «починка успешна».
2. **Свой процесс, починка не удалась.** Файл остаётся занятым после перезапуска процесса. Пользователь видит одно сообщение с четырьмя частями из Т4 и тремя кнопками. Слов «неизвестная ошибка» в нём нет.
3. **Чужая программа.** Файл занят сторонним процессом, например антивирусом. Программа его не завершает. В сообщении названо имя этого процесса.
4. **Повторные команды.** После сбоя пользователь отправляет ещё пять команд. Новых сообщений об ошибке не появляется, статус «команды недоступны» остаётся на месте, агент отвечает, что выполнить команду сейчас нельзя.
5. **Восстановление.** Причина устранена вручную. После нажатия «Проверить снова» статус исчезает, следующая команда выполняется без перезапуска программы.
6. **Песочница не отключается.** Ни в одном из сценариев 1–5 команда не выполняется вне песочницы без отдельного подтверждения пользователя.
7. **Отчёт.** В тексте отчёта нет имени пользователя, имени компьютера и путей к рабочим папкам. Два отчёта с одной подписью дают одну запись со счётчиком 2.

## Метрики успеха

Главная метрика: доля сбоев песочницы, после которых пользователь смог продолжить работу в песочнице в той же сессии. Остальные показывают, за счёт чего она меняется и не стало ли хуже.

| Метрика | Как считаем | Чего ждём |
| --- | --- | --- |
| Восстановление в сессии | Сессии, где после события «проверка не пройдена» была успешная команда в песочнице, делим на все сессии с этим событием | Рост. В разобранном случае оно близко к нулю: перезапуск не помогал |
| Самопочинка | Сбои типа «занято своим процессом», устранённые без показа сообщения, делим на все сбои этого типа | Большинство. Точную цель ставим после первой недели данных |
| Дубли обращений | Доля публичных обращений об одном сбое в общем потоке за период инцидента | Снижение. Точка отсчёта: 23% за три дня |
| Время до ясности | Время от первой неудачной команды до показа сообщения с причиной | Секунды. Сейчас пользователь причину не получает вовсе |
| Сторожевая: работа без защиты | Доля сессий, где после сбоя включили полный доступ | Не растёт |

У меня нет доступа к внутренней статистике продукта, только к публичным обращениям. Поэтому из пяти метрик точка отсчёта известна только для дублей. Остальные четыре сначала надо измерить, для этого и нужно требование Т9.

## Границы, риски и открытые вопросы

**Что не входит в спеку**

- Исправление самой ошибки в Codex. Это задача его разработчиков, а спека о том, как продукт ведёт себя при любом похожем сбое.
- Сбои внутри команды, когда песочница запустилась, но запретила нужное действие.
- macOS и Linux. Там механизмы другие, и данных о похожем сбое у меня нет.

**Риски**

- Перезапуск служебного процесса может прервать то, что агент делает в этот момент. Нужно перезапускать только простаивающий процесс или предупреждать пользователя.
- Проверка при запуске замедляет старт. Её нужно выполнять в фоне и не блокировать окно.
- Сообщение «проблема известна» требует, чтобы команда быстро помечала известные подписи. Без этого процесса пункт будет пустовать.
- Фрагмент журнала в отчёте может содержать личные данные помимо имени в путях.

**Открытые вопросы**

- Сколько пользователей столкнулись со сбоем на самом деле? Обращение пишет меньшинство, и 177 обращений задают только нижнюю границу.
- Какие ещё причины сбоя настройки встречаются часто? Список типов в Т2 составлен по одному инциденту.
- Можно ли безопасно разрешить команды только на чтение, пока песочница не работает? Это вернуло бы часть пользы, но решение за командой безопасности.
- Публичная страница статуса или сообщение только внутри приложения?

## Источники и метод

Данные: 784 последних обращения из репозитория [openai/codex](https://github.com/openai/codex/issues) на GitHub, выгружены 10 октября 2026 через открытый интерфейс GitHub. Это часть исследования 2 699 обращений к шести ИИ-инструментам для кода.

Как найдены 177 обращений: поиском по заголовку и тексту любой из пяти строк: `setup refresh had errors`, `os error 32`, `sharing violation`, `node_repl.exe`, `ACL validation`. Модель в этом подсчёте не участвовала.

Ограничения:

- период всего три дня, и это разгар инцидента, а не обычная неделя;
- поиск по строкам мог захватить обращения, где файл упомянут по другому поводу, и пропустить те, где ошибка описана своими словами. Целиком прочитаны только четыре самых обсуждаемых;
- причина сбоя взята из описаний пользователей.

Все цифры исследования собраны на [дашборде](https://gmqzns-droid.github.io/ai-devtools-research/), код и данные лежат в [репозитории](https://github.com/gmqzns-droid/ai-devtools-research).
